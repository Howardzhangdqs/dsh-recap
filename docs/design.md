# dsh-recap 设计说明

本文说明 dsh-recap 的设计：要解决什么问题、核心机制如何工作、每个关键决策背后的取舍。不涉及实施过程；具体行为以代码为准。

## 1. 要解决的问题

长编程会话动辄包含几十上百次模型请求。想知道「这个会话做了什么」，只能从头重放整个对话——上下文长、噪声多（工具调用参数、执行结果、思考过程都在其中），人工阅读的成本很高。

dsh-recap 把**每一次模型请求（turn:step）新增的数据**总结成一句话，按时间顺序追加成一条「回顾链」。回顾链本身就是会话的时间线摘要：读链即可知全局，需要细节时再按每句携带的坐标（`[T<turn>:S<step>]`）回到原对话定位。

真正的难点在于「增量」与「低成本」要同时成立：总结发生在会话进行中，每次生成都需要之前的全部历史作为上文；若每次都把历史原文喂给模型，输入长度与费用会随会话线性膨胀，最终超出上下文窗口。核心设计（第 3 节）就是围绕这一点展开的。

## 2. 设计约束

插件运行在活跃的 agent loop 中，这一事实决定了三条硬约束：

1. **零 agent loop 侵入**。捕获是对 `session/event` 的只读监听；生成是与主循环并行的辅助调用（`ctx.llm.stream`，`purpose: 'recap'`）。主循环永不等待总结——总结的快慢不能影响会话本身。
2. **无思考生成**。总结是一句话改写任务，不需要推理链。总结调用默认 `reasoningEffort: 'off'`；不支持 `off` 的路由自动降为 `low`。
3. **零会话足迹**。不向会话日志追加事件、不注入消息，持久化走插件自有文件（`~/.dsh/recap/sessions/<sessionId>.jsonl`）。会话日志属于用户与主循环，插件不应污染它；插件产生的全部数据只写入自有文件，与 DSH 的会话数据完全隔离。

## 3. 核心设计：增量总结与前缀缓存

### 3.1 两个朴素方案为什么不行

把「历史 + 新数据」交给模型总结，直观做法有两种，但都不成立：

- **重放原文**：每次都带上之前所有请求的原始数据。模型确实能看到完整上下文，但输入随步数线性增长（实测约 640 token/步），第 100 步时单次输入已超过 6 万 token——迟早超出上下文窗口，费用也随之膨胀。
- **只喂新数据**：每次只带本次新增的 Δ，不带历史。输入确实短，但模型不知道之前总结过什么，新句无法与历史衔接，还会重复；而且（见 3.3／3.4 的对比）这种排布会把 provider 的前缀缓存完全浪费掉。

本设计在两者之间取平衡：**历史以已总结的句子形式进入提示词**（每句约 40 token，而非其对应的约 600 token 原文），并把提示词排布成对 provider 前缀缓存最友好的形状。

### 3.2 提示词结构

第 k 次总结调用的消息结构如下（`system` 指令与结尾指令在一条链内逐字节不变）：

```
system:    固定指令（记录员角色、输入结构说明、写作风格、输出要求）
user:      1. R1                        ← 已定稿句子的裸编号行，逐字来自存储
           2. R2
           …
           k-1. Rk-1
           <new_delta>
           {…Δk 的严格 JSON…}
           </new_delta>
           请总结本次模型请求的数据，输出下一句。
assistant: Rk                           ← 模型只输出下一句
```

system 指令要求模型只针对 `<new_delta>` 中的新增数据写**恰好一行**自然叙述（不超过 60 个 CJK 字符或 30 个西文单词），风格像同事复述刚完成的工作：主谓宾完整，禁止电报式压缩与缩写堆砌。历史行被明确声明为只读，禁止改写或复述。

### 3.3 排布理由：前缀缓存如何被最大化

provider 的前缀缓存按**从第 0 字节起逐字节匹配**计费：输入开头与近期请求相同的部分按缓存命中价计费，首个差异点之后的全部内容按全价。因此设计目标可以精确表述为：**让相邻两次调用的输入，在尽可能靠后的位置才出现第一个字节差异**。

本结构下，第 k 次与第 k+1 次调用的输入分别为：

```
第 k 次:   system + 句子行 1..k-1 + <new_delta>Δk</new_delta> + 指令
第 k+1 次: system + 句子行 1..k-1 + 句子行 k + <new_delta>Δk+1</new_delta> + 指令
```

两者共享 `system + 句子行 1..k-1` 的逐字节前缀，首个差异点精确落在**最新一句**上。也就是说，除「一行新句 + 本次的 Δ（本来就必须输入的新数据） + 结尾指令」外，其余输入全部命中缓存。

这个结果依赖两个具体决策：

- **历史在前，Δ 在尾**。Δ 每次都不同；若放在开头，首个差异点会提前到 system 之后，其后所有内容每次都按全价计费，前缀缓存形同虚设。
- **历史用裸编号行，不用闭合标签包裹**。若用 `<recap_history>…</recap_history>` 包裹历史，闭合标签的字节位于最新一句**之后**，每次追加新句时这部分都要重新计价（每次约 18 字节的永久性未命中）；更重要的是裸行使历史成为严格只追加的文本——第 k 次调用的全部历史行，就是第 k+1 次调用历史的逐字节前缀。`<new_delta>` 开标签起自定界作用，不需要历史块自己闭合。

### 3.4 token 核算

以 k=100 步、Δ≈600 token、每句≈40 token、system≈150 token 为例：

| 方案 | 每次调用输入 | 其中命中缓存 | 未命中（全价） |
|---|---|---|---|
| 重放原文（全链多轮） | ~64,150 | ~63,550 | ~600 |
| Δ 前置（携带历史，Δ 放在历史之前） | ~4,710 | ~150 | ~4,560 |
| **本设计（裸行历史＋Δ 在尾）** | **~4,710** | **~4,070+** | **~640** |

三种方案的取舍一目了然：重放原文命中率不低，但输入本身线性增长（约 640 token/步），迟早超出上下文窗口；Δ 前置输入长度与本设计相同，但首个差异点提前到 system 之后，几乎全部按全价计费；本设计输入短（约 4,700 token）且命中率高，未命中部分≈本次 Δ（约 600，无论如何都要支付）＋一行新句。输入长度每次调用仅增长约 40 token（一句的长度），长会话不会超出窗口；历史超过 `historyMaxSentences`（默认 400 句）时折叠最旧的句子，输入长度有硬上界。

### 3.5 前缀稳定性的工程保障

缓存前缀是易碎品：任何一处字节变化都会使其后的全部内容失效。保障措施：

- **落盘句子即前缀材料**：存储文件中的句子文本，就是下次调用时逐字进入提示词的文本，中间不做任何转换。
- **序列化确定**：句子行固定为 `"{i}. {sentence}"`；生成结果先经规范化（取首个非空行、剥离编号/引号/加粗、折叠空白、160 字符硬上限）再落盘，杜绝格式噪声进入前缀。
- **Δ 封装确定**：固定 JSON key 顺序、固定截断规则、不含时间戳或随机值。
- **链内常量**：路由、effort、`maxTokens`、system 指令在一条链内保持不变——修改其中任何一项都等于更换前缀，缓存一次性失效（这也是部署参数应尽量在会话开始前配好的原因）。
- **可验证**：每次调用的 `usage.cacheReadTokens` 随条目落盘，UI 显示命中率徽标，设计承诺可以实际核对。

## 4. 数据管道

```
session/event ──▶ capture（seed 回放 + live 镜像，按消息 id 幂等去重）
                      │ 每 step 的 Δ（新增数据，确定性截断 + JSON 结构化封装）
                      ▼
                 queue（会话内串行、跨会话并行、背压合并、失败容错）
                      │ history = store 中的句子（逐字节复用为前缀）
                      ▼
                 generator（ctx.llm.stream 辅助调用，purpose:'recap'，
                      │    reasoningEffort off→low，超时控制）
                      ▼
                 store（~/.dsh/recap/sessions/<sid>.jsonl，追加写 + 压缩）
```

### 4.1 捕获（capture.ts）

- **双源合并**：**seed**（`ctx.sessions.get(sid).events` 快照回放，覆盖宿主重启之前的历史）＋ **mirror**（`session/event` 追加流，覆盖存储水合的延迟）。live 事件在 seed 完成前先缓冲，保证不丢。
- **幂等**：`seenIds`（消息 id＋`call:` id）与 `emittedKeys`（step key）双重去重——同一事件从两个来源先后到达均为空操作。
- **归属规则**：每条新数据进入**产生它的那个 step** 的 Δ——该 step 消费的用户输入、它组装的 assistant 消息、它发起的 tool call 与结果。`user/message` 事件没有 turn/step 标签，先进入 pending 队列，由下一个 `step/start` 归属；turn 结束时仍未归属的数据以 `turn:tail` Δ 的形式输出。带工具调用的 step 有完成门控：`step/end` 到达时若仍有未返回结果的调用，该 step 的 Δ 暂存，最后一个工具结果落地后才真正提交；turn 结束仍未返回的（调用被中断），在 `turn/end` 强制输出。
- **compaction 安全**：压缩替换产生全新的消息 id，自然作为新 Δ 处理；被替换的旧消息不再出现，无需特殊逻辑。
- **重启恢复**：用存储条目的 `itemIds`/`key` 初始化去重集合，重启后的回放不会为已总结过的 step 重新生成。

### 4.2 排队（queue.ts）

- **会话内串行、跨会话并行**：串行保证句子的生成顺序与存储顺序一致（这正是缓存链的顺序）；跨会话互不影响。入队路径 fire-and-forget，主循环零等待。
- **触发**：`step-end`（默认，防抖 1.5 秒，请求一结束即总结，句子随请求生成）/ `turn-end`（turn 结束后防抖合并成批）/ `manual`。
- **失败容错**：单条失败记为 `failed` 条目，其 itemIds 仍视为已处理（不无限重试），链条继续；连续 3 次失败则暂停，等待下次触发。
- **限流重试**：生成请求遇到 `RATE_LIMIT`（如 zai 的 429/1305「访问量过大」）时不记录失败，而是把该 Δ **原样排回队首**等待重试——回顾链不会留下永久缺口。退避按 `retryBackoffMs` 为基数指数增长（连续限流每次翻倍，上限 32 倍基数），等待期间 UI 在对应位置显示「限流等待中，Ns 后重试…」。
- **背压**：待总结 Δ 超过 `maxPending`（200）时，在入队时合并最旧的条目（合并条目 key 形如 `merged:<首条key>..<末条key>`，如 `merged:1:1..1:3`），内存占用有界。
- **路由优先级**：设置页显式指定的 provider+model → 会话记录的路由 → 宿主默认模型。

### 4.3 生成（generator.ts）

- **辅助调用**：`ctx.llm.stream` 直调（与 dsh-session-title-llm 同一模式），`purpose: 'recap'` 标记（核心与适配器均容忍未知值，已验证；任何观察者可据此过滤）、`maxTokens: 120`、deadline 超时、AbortSignal 级联取消。
- **effort 阶梯**：`off` →（路由拒绝时一次性降级）`low` → 按路由记住生效档位；`follow` 直接省略该字段。模型完全没有 effort 词表时任何显式值都会被拒，此时阶梯终点是省略。DeepSeek 适配器把 `off` 映射为 `thinking: disabled`。
- **输出规范化**：取首个非空行、剥离编号/引号/加粗、折叠空白、160 字符硬上限；空输出、工具调用输出或异常 finish 均按错误处理。

### 4.4 存储（store.ts）

- 每会话一个 JSONL 文件（遵循 `DSH_HOME`），一行一条：`{v, index, key, turn, step, createdAt, sentence?, status, error?, route?, usage?, itemIds, callIds?, deltaStats}`。
- 追加写（每会话用 promise 链串行化）；坏行跳过；超过 `storeMaxEntries×2` 时以 write-temp＋rename 方式压缩回上限。
- `sentences()` 重建提示词前缀；`coveredIds()`/`coveredKeys()` 重建重启恢复所需的去重集合。

## 5. 对外接口

- **HTTP**（`POST /recap/api/<method>`，JSON body；与 `/api` 使用相同的 Host 头/trustedHosts 信任校验）：`list`（条目＋汇总＋队列状态）、`generate`（手动排空）、`stats`、`clear`、`settings`/`settings.update`（带 revision 并发守卫）、`providers`（路由选择器数据源）。
- **设置**：宿主侧把 `recap` 命名空间注册进 DSH 设置服务（持久化、校验、watch）；设置界面条目由客户端经 `settings.section` 槽注册的分区提供，读写走上述自有路由——DSH 的 settings RPC 不向配置客户端开放第三方命名空间，这是必须绕行的原因。
- **模型工具**（`toolsEnabled`，默认关闭——开启后工具 schema 会随会话请求发送）：`recap_read(limit?)` 读取回顾链、`recap_refresh()` 立即排空队列，作用域按 `exec.agent.session.id` 绑定到对应会话。
- **UI**：对话内联回顾行——主路径为 React 委托（接管 assistant-step 与 tool-call 槽位＋turnTail 链），DOM 锚定注入为后备；句子插在产生它的那次请求之后（带调用的请求锚定到其最后一个工具行之后）。zh/en 双语，跟随 DSH 语言设置。

## 6. 零足迹保证

零会话足迹（约束 3）通过以下不变量保证，均有对应实现与测试：

1. 捕获监听器同步透传、零改写（事件对象本已冻结）；
2. 生成不调用 `agent.inject`、不向 surface 追加、不调用 `session.append`——会话日志零新增事件；
3. 触发全部来自事件监听，fire-and-forget；异常只记录到 logger 与 `failed` 条目；
4. 总结请求带 `purpose: 'recap'` 且不属于 agent loop 请求，任何观察者可过滤；
5. 模型工具默认不注册（避免工具 schema 进入会话请求）；
6. 文件 I/O 全异步、每会话串行；背压合并最旧的待处理项；
7. 会话 dispose 时中止生成并落盘；所有定时器与监听器都有 disposer（HMR 安全）。

## 7. 工程组织

单一包内分为宿主端与客户端两部分：宿主端（`src/`）承载捕获、队列、生成、存储、HTTP 路由与模型工具；客户端（`src/client/`）承载界面与 i18n。构建上 `tsdown` 产出双通道 client bundle（profile 名 `dsh-recap` 与注册表 id `dsh-external/dsh-recap`），类型声明走 `tsc -p tsconfig.build.json`。外部依赖仅 peer 解析 `@deepseek-ai/dsh-llm`（BlockAssembler/createUserMessage/ReasoningEffortId）与 `schemastery`（Config schema）。DSH 的 ctx 类型通过结构化镜像补齐（`context-types.ts`），上游类型变化的影响被限制在这一个文件内。测试覆盖 capture/store/generator/queue 四个模块的接缝与插件形状一致性。
